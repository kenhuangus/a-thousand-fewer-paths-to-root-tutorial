The Target

Why the Linux Kernel?

One codebase sits underneath Android phones, cloud infrastructure, and supercomputers — billions of people depend on it. A single local privilege escalation (LPE) there is a path from an unprivileged user to root: total control of the machine.

0M+
lines of code in the Linux kernel
4
major attack surfaces: system calls, networking, filesystems, device drivers
root
the prize — an LPE crosses the kernel's core security boundary

Where the work piled up

Models can produce thousands of candidate findings in hours. Each candidate still needs a person to check three things: does the bug reproduce, does it cross a security boundary, and should a maintainer see it before the others? That checking is the slow part, and it does not speed up just because the candidate list grows.

The research question

OpenAI built a prototype to test how effectively frontier models could find vulnerabilities and demonstrate their security impact in a codebase of this scale — inside a controlled research environment, reporting to maintainers through the Patch the Planet initiative.

Where most of the work went

Spotting a suspicious line of code was not the hard part. The hard part came after it. The team had to test each of the 2,308 candidate findings, prove which ones gave an attacker root, write 948 patches, and give the kernel maintainers evidence they could check for each bug.

What leaves the pipeline

For every vulnerability, the system bundles four artifacts for the human reviewer:

  • Root cause analysis — why the bug exists
  • Minimal crashing PoC — the smallest trigger
  • A full exploit — proof of real security impact
  • A candidate patch — ready for maintainer review

Why the bundle matters

A maintainer who receives a reproducer, a working exploit, and a patch can check the bug's severity in minutes. A maintainer who receives only a written description has to redo the analysis from the start. The bundle is what let OpenAI send reports at this volume.

Tech detail — why reachability is the filter

A memory bug in code that only root can run cannot give an attacker root — the attacker is already there. So the scouts apply the threat model — the code must be reachable by a low-privileged user with no special capabilities — before the team spends money on the analyst stage.

Stage 2 · Dynamic Validation

Prove It Crashes: The KASAN Loop

At this stage, a candidate finding is only a claim. A triage agent writes a proof-of-concept program, runs it in an isolated VM running a KASAN kernel (Kernel Address Sanitizer), reads the console output, and repeats the cycle until the bug triggers or the agent gives up.

What happened to the other 25.3%?

Most findings that did not reproduce were not wrong. They needed elevated privileges, or they depended on hard race conditions, specific allocation-failure points, or triggers too slow for the time budget (such as refcount wraparound). One cost fact stands out: checking a false positive costs about the same as checking a true finding, so the team saves money when it drops bad candidates early.

Tech detail — the screening agent is deliberately permissive

Before ExploitDev, a screening agent reads each report, crash log, and source code without running anything, and keeps every finding that might lead to an exploit. The team set the screener to keep too much rather than throw away a serious finding. The expensive ExploitDev stage then ran only on the 1,551 findings that passed (313 + 1,238). Screening cost: $44,194.

Failed attempts cost over 10× more than successful ones

Each of the 1,169 successful exploits cost about $359 on average. Each of the 69 failed attempts cost $3,922 on average, because the agents kept working on hard cases such as race conditions. OpenAI wrote that a stop rule — end an attempt after one hour with no progress — would have cut that cost.

LPEs cost ~2× info leaks

Per candidate processed: $558 for an LPE vs $271 for an info leak. Info-leak PoCs carried over from validation nearly ready; an LPE exploit needs strategy planning, target-object selection, and mitigation bypasses on top.

OpenAI called these costs an upper bound. The team set the runs up to measure what the model could do, not to keep costs down, and OpenAI expects better tooling around the model to lower the cost of every stage.

The orchestration experiment

GPT‑5.5 Cyber didn't reliably know when to apply known kernel exploitation techniques. Giving it a library of 103 techniques lifted success on 63 candidates from 76.2% → 88.9%.

GPT‑5.6 Cyber found and applied techniques on its own. The lightly orchestrated 5.6 workflow beat the heavily scaffolded 5.5 one — and adding the technique library back gained only +1.5 points.

What the three runs show

  • A stronger model found vulnerabilities in code that an earlier model had already checked and passed over — same setup, same codebase.
  • The extra tooling that raised one model's score added almost nothing for the next model, so a team has to re-measure its tooling each time the model changes.

10 Techniques Nobody Had Seen

OpenAI sampled 166 agent-written exploits and audited the techniques inside them. Ten were new — confirmed novel by third-party kernel exploitation experts.

The 10 novel techniques, by class

Full technical details withheld by OpenAI for safety; classes as reported.
5 · Data-only attacks 2 · Persistent elastic objects 2 · Page grooming 1 · Arbitrary type confusion

What each class does

  • Data-only (5) — the exploit corrupts kernel data and never takes over control flow. It reaches root either directly or through an arbitrary write. Because the attack never redirects execution, defenses that guard control flow do not stop it.
  • Persistent elastic objects (2) — new kernel objects the agents sprayed into the target cache to shape heap layout reliably.
  • Page grooming (2) — new ways to arrange memory pages so the vulnerable object lands where the exploit needs it, raising reliability.
  • Type confusion (1) — an arbitrary type-confusion primitive: the kernel treats an object as the wrong type, opening the door to further corruption.
What this shows

The agents did more than copy known exploits. In 10 cases they produced techniques that outside experts checked and confirmed nobody had published before. A defender who runs the same kind of model can find these techniques in a lab, before an attacker uses them on a live system.

Stress test: Google's kernelCTF

A second run targeted kernelCTF — a hardened kernel with a reduced attack surface, under the program's real rules:

  • 21 LPE exploits + 25 info-leak PoCs in 112 hours
  • For scale: only 26 confirmed 0-day LPEs had been accepted by kernelCTF in all of 2026
  • Total cost $32,936 (discovery was 83.7% of it) → a potential ~$1.5M bounty, ≈ 45× cost
  • One config change: SLAB_VIRTUAL was dropped — the stock kernel build was incompatible with it

Why OpenAI ran the numbers this way

An attacker can buy the same kind of model time. A vulnerability that a defender finds and fixes first gives that attacker nothing. OpenAI stated its goal in cost terms: defenders fix enough bugs that an attack costs more than it pays.

What these figures are, and what they are not

Nobody paid $18.9M–$66.3M. OpenAI multiplied the 948 exploits by historical bounty rates to estimate their value, and the kernelCTF payout would depend on the program accepting the exploits. The costs — $1,213,430 and $32,936 — are the amounts the team actually spent.

The Cautionary Tale

The Wrong-0-Day Trap

The pipeline counted a vulnerability as “exploited” when the agent got a root shell. In an early run, that count was wrong in 20 cases: the agent had reached root through a different bug than the one it was assigned.

✗ Result-only verification

The team assigns bug A. The agent reaches root through an unrelated bug B that it found on its own. The dashboard records “A exploited.” The team then writes the report, the severity rating, and the patch for the wrong vulnerability.

→

✓ Check which bug the exploit used (the fix)

OpenAI tightened the task rules and added a separate check. The check confirms that each finished exploit triggers the vulnerability the team assigned to that agent. The team counts a root shell as a success only when the check passes.

Why the check matters

A team that records only the final result — root shell or no root shell — cannot tell a real success from a wrong one. OpenAI's reviewers caught the 20 wrong cases because a separate check confirmed which bug each exploit had used. The same gap can sit inside any agent test that scores the result and never checks how the agent got it.

Patch generation, second version

The model's first patches fixed the bugs but had faults: more code than the fix needed, slower performance in places, style that did not match the surrounding code, and missed variants of the same bug. OpenAI added clearer instructions, automatic code checks, examples of nearby kernel code style, and variant analysis. The second version produced patches that fixed the bug with less code and matched kernel style. In a few cases the prototype also caught flaws in patches written by people before those patches were merged.

Two things the run forced the team to do

  • Check each finding again before reporting it. The team re-checked findings against the current upstream code. Without that step, the team would have sent maintainers reports for bugs that other developers had already fixed.
  • Check the test machines, not only the kernel. In the kernelCTF run, an agent traced an unexpected crash to a QEMU TCG vulnerability — a bug in the emulator that ran the test, not in the kernel — and exploited that bug. The models found bugs in the team's own test setup as well.

Per the kernel community's guidance, OpenAI reported critical vulnerabilities first and is working through the rest with Patch the Planet partners.

Synthesis

Six Points From the Report

The main results of “a thousand fewer paths to root,” stated in plain terms.

1 · The models found candidates fast. The checking took the work.

The Analyst agents produced 2,308 candidate findings. The steps after that took most of the time and money: the team ran proof-of-concept programs to reproduce each bug, tested whether each bug could give an attacker root, wrote a patch for each confirmed bug, and collected the evidence a maintainer needs to review the report.

2 · Check which bug an exploit used, not only whether it reached root

In an early run, 20 of 200 exploits reached root through a different 0-day than the one the team had assigned. OpenAI added a separate check that confirms each exploit triggers its assigned bug before the team counts the exploit as a success.

3 · Failed attempts cost far more than successful ones

The 69 failed exploit attempts cost $3,922 each on average. The 1,169 successful exploits cost about $360 each. OpenAI wrote that stopping an attempt after about one hour with no progress would have cut the cost of the failed attempts.

4 · A stronger model found bugs the earlier model missed

The July scan found 166 distinct LPEs in the kernel. The October scan used a stronger model on the same codebase with the same basic setup and found 948.

5 · Help that one model needs may add little for the next model

Giving GPT‑5.5 Cyber a library of 103 known techniques raised its success rate by 12.7 points. The same library raised GPT‑5.6 Cyber's rate by only 1.5 points, because that model found and applied techniques on its own.

6 · Finding a bug cost far less than the bug's bounty value

The pipeline cost about $1,280 for each distinct LPE it found. Historical bounties for one kernel LPE run from $20,000 to $70,000. That gap holds only for bugs that get fixed before an attacker finds them — an attacker can run the same kind of pipeline.
